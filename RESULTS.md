# Benchmark results

Sorted IndexMap was the fastest deterministic option for four of the five selected dep-info files and for the complete corpus. BTreeMap won on the smallest fixture, but made reconstruction of Cargo's encoded fingerprint substantially slower. These are local operation costs, not end-to-end Cargo build times.

The measurements below come from the committed [original interleaved samples](results/original/interleaved.csv). They predate standalone packaging and do not include later verification runs.

## Method

- Inputs: 316 real rustc dep-info files generated by `cargo check --lib --locked` on Cargo, containing 3,987 distinct paths summed across compilation units. The largest file by path count has 223 paths.
- Source: Cargo revision [`cf29d0e0`](https://github.com/rust-lang/cargo/tree/cf29d0e0b1f7b03c4ceda5211cc4dc493bfc542e). Source and fixture checksums are recorded in [provenance.json](provenance.json).
- Host: Intel Core Ultra 9 285H, Linux x86-64, pinned to CPU 0.
- Toolchain: rustc 1.99.0 (`b940084d7`), Cargo 1.99.0 (`5f94df478`). Release optimization level 3, debug information disabled.
- Initial run: Criterion 0.8.2, 50 samples per case, 0.5-second warmup, and a requested 2-second measurement period.
- Cross-check: 30 interleaved rounds with shuffled case order and batches calibrated to approximately 20 milliseconds. This reduced sensitivity to the timing drift observed in the sequential run.

All tables report the median of the interleaved per-round times per operation, in microseconds (`us`). Lower is better. The corpus row measures one pass over all 316 files, not an average file. CPU frequency and unrelated system activity were not controlled, so small differences should not be treated as statistically established improvements.

See [environment.json](results/original/environment.json) for run settings and [the Criterion estimates](results/original/run1-summary.json) for the initial run's means and confidence intervals. Those estimates use a different summary statistic from the tables here.

## Parse and encode

The current-hasher cases compare FxHashMap with BTreeMap, Fx-hashed IndexMap sorted after parsing, and FxHashMap with sorting of the existing encoded-files vector before serialization.

| Input | Paths | FxHashMap baseline (us) | BTreeMap (us) | IndexMap + load sort (us) | HashMap + write sort (us) |
|---|---:|---:|---:|---:|---:|
| cargo-credential | 5 | 1.389 | 1.486 | 1.875 | 1.718 |
| http | 20 | 9.331 | 14.819 | 13.985 | 16.534 |
| syn | 54 | 24.451 | 55.279 | 48.551 | 55.580 |
| gix | 179 | 96.111 | 250.250 | 212.421 | 242.108 |
| cargo | 223 | 56.996 | 237.420 | 139.967 | 194.464 |
| Complete corpus | 3,987 total | 2447.785 | 4476.758 | 3964.675 | 4774.210 |

The baseline does not enforce canonical ordering. Every deterministic alternative added work relative to it in these measurements. Path count alone does not explain timings: the fixtures differ in path lengths, prefixes, input order, and environment entries.

## Encoded reads and filesystem work

Both operations below use the 223-path Cargo fixture. Encoded reads decode preloaded binary data and reconstruct the collection with absolute paths. The warm-path operation parses text, canonicalizes source paths against the capturing machine's checkout, and encodes the result. It excludes dep-info file reads and writes.

| Variant | Encoded read (us) | Parse + warm canonicalization + encode (us) |
|---|---:|---:|
| FxHashMap baseline | 53.614 | 838.124 |
| BTreeMap | 290.538 | 1019.390 |
| IndexMap + load sort, FxHash | 51.406 | 929.626 |
| HashMap + write sort, FxHash | 52.364 | 987.403 |
| HashMap baseline, standard hasher | 62.263 | Not measured |
| IndexMap + load sort, standard hasher | 59.238 | Not measured |
| HashMap + write sort, standard hasher | 62.129 | Not measured |

BTreeMap's encoded-read time was 5.42 times the current FxHashMap baseline. This matters because changing `RustcDepInfo.files` affects fingerprint reads during freshness checks as well as writes after compilation. The small read-time differences among the other current-hasher variants do not establish a speedup. The IndexMap read case retains the order of the already-sorted encoded input without an additional sort.

The filesystem measurements are specific to the original checkout and warm filesystem state. They are not portable timing baselines.

## Correctness and reproducibility

All ordered variants produced byte-identical encodings across the 316 fixtures, including reversed dependency order. Separate checks covered escaped paths, duplicate paths, checksum updates, and environment values.

The recorded [eight-clean-build experiment](results/original/reproduction.json), using Cargo 1.99.0, produced one distinct fingerprint dep-info encoding and one distinct `.rustc_info.json` encoding. The rustc-cache JSON was also logically identical across all eight builds.

Reversing dependency insertion order changed the extracted FxHashMap encoding for 207 fixtures. That demonstrates input-order sensitivity; it does not reproduce differing output from identical inputs in actual clean builds. [Cargo #17169](https://github.com/rust-lang/cargo/pull/17169) removed the per-instance randomized hashing behind the original report. These experiments did not establish a remaining same-input clean-build bug after that change.

## Interpretation and limits

- The results do not support treating a blanket BTreeMap replacement as performance-neutral. It affects the repeatedly used read path as well as construction and writing.
- Sorted IndexMap was the strongest deterministic option for the larger retained-path workloads measured here.
- Sort-on-write remains a narrower implementation option. Production Cargo can sort after normalization and filtering, avoiding work on discarded registry-package source paths. The primary benchmark retains all paths, so it does not measure that advantage.
- The primary cases operate on preloaded inputs and retain all environment entries. They exclude filesystem I/O, canonicalization, and compiler work. The corpus-wide timings are not estimates of total Cargo overhead.
- The real corpus has no checksum comments. Checksum handling was verified for correctness, but checksum-heavy performance was not measured.
- No `.rustc_info.json` serialization benchmark was run. Its bytes were checked only in the clean-build experiment.

These measurements compare collection strategies. They do not establish an end-to-end build-time winner or justify a reproducibility fix without an updated reproducer for current Cargo.

## Recompute the summaries

From the workspace root:

```sh
python3 summarize.py --interleaved results/original/interleaved.csv
python3 summarize.py run1 --criterion-root results/original/criterion
```

The commands read the committed measurements and write summaries under `results/local/`. They do not rerun the benchmarks. See the [README](README.md#run) to collect new measurements.
